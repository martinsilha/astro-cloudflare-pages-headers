# Why an Astro page can miss your Cloudflare header rules

Draft for review. Targets `astro-cloudflare-pages-headers` v2.0.0; not published.

A static page and a server-rendered page can share a hostname and still take different paths through Cloudflare. That matters when you configure response headers.

For a static asset, Cloudflare reads `_headers` from the deployed asset directory. For a response generated by Worker code, that file does not apply. Cloudflare documents this boundary for both [Workers static assets](https://developers.cloudflare.com/workers/static-assets/headers/) and [Pages Functions](https://developers.cloudflare.com/pages/configuration/headers/). A matching URL rule alone does not make the asset service process a response produced by application code.

This becomes visible when an Astro site mixes prerendered pages, static CSS and on-demand pages or API endpoints. A header can appear on one response and be absent on another even though the route patterns look correct. The first useful question is: which layer produced this response?

## Two places to apply shared defaults

You can maintain `_headers` for assets and add headers yourself in server code. `astro-cloudflare-pages-headers` v2 provides another option for Astro projects: declare shared defaults once and apply them at both relevant layers.

```js
astroCloudflarePagesHeaders({
  headers: {
    'X-Content-Type-Options': 'nosniff',
    'Referrer-Policy': 'strict-origin-when-cross-origin',
  },
})
```

This is the integration entry in `astro.config.mjs`, using the package's default export. During the build, it writes the configured rules into the resolved static asset output. When the official Cloudflare adapter is present, it also registers middleware that adds missing headers to responses handled by Astro. The [complete static and SSR examples](../guides/static-and-ssr.md) include the imports, adapter configuration and a test endpoint.

A static-only project needs no adapter for `_headers` generation. For Astro 6 and 7, Cloudflare SSR uses Workers; a static site can still use Pages. The package supports stable Astro 4–7, with an adapter version compatible with the chosen Astro release.

## The application keeps the final say

An endpoint may need `Cache-Control: private, no-store`, or a page may produce a nonce-bearing CSP for its actual HTML. Runtime middleware preserves a header already present on that response, using case-insensitive names. Shared configuration fills missing values; it does not force a policy over the application.

That distinction also means a broad cache rule deserves care. Do not make every SSR response publicly cacheable just to speed up static assets. Scope long-lived caching to fingerprinted assets, and keep user-specific cache decisions in the code that creates those responses. Multiple matching configured rules combine values, so narrower rules are not a substitute for removing a contradictory broad rule.

The runtime layer reads the integration configuration, not manually authored `_headers` content. Existing file rules remain preserved for static delivery. If a default should cover both layers, declare it in `headers`.

## CSP still depends on the content you serve

The integration can optionally hash inline content in generated HTML at build time. It does not buffer or hash dynamic SSR HTML. Runtime pages still need a CSP appropriate to their actual content, including application-generated nonces where required.

Astro native CSP and an integration-owned CSP response header are separate policies. Enabling both does not let one relax the other. Choose an owner for script/style policy and verify the result in a browser. The package supplies neither a universal security policy nor an automatic fix for unsafe application content.

## Check both response paths

Build first and inspect `_headers` in the asset directory that will actually be deployed. Then, in your normal preview environment, make GET requests to a real asset URL and a known Astro endpoint. Inspect headers as well as status and body. Confirm that an endpoint's own cache policy survives, and use browser checks for CSP behavior. Development-server responses alone do not demonstrate Cloudflare's asset handling.

The boundary remains: Astro middleware cannot affect platform-generated redirects, custom Worker paths that bypass Astro or exceptions not converted into Astro responses. Nor does it create CORS preflight routes. Those cases belong to the layer producing the response.

If you are already using v1, the [migration walkthrough](../migrations/2.0.md#upgrade-an-existing-project) shows how to move from `server.headers` to explicit integration configuration without changing your Astro major version. Start with a small set of shared defaults and verify each response path before adding more policy.
