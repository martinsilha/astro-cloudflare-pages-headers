# Migrating to 2.0

Version 2.0 prepares this integration for current Astro releases and Cloudflare Workers. It changes package delivery and makes the integration's static and runtime header behavior explicit.

## Upgrade an existing project

Start on a branch and keep your current Astro/adapter pair unless you are deliberately upgrading it too. Moving to v2 does not require moving to Astro 7.

1. Install `pnpm add astro-cloudflare-pages-headers@^2` and review the lockfile change. Keep imports pointed at the public package root.
2. Move shared header rules into the integration's `headers` option. The compatibility fallback to `server.headers` still works, so you can do this separately from the version upgrade.
3. Decide whether the new runtime defaults are appropriate. With the official Cloudflare adapter, leave the default to cover Astro responses, or set `runtime: false` to retain static-only behavior.
4. Build and inspect the generated `_headers` in the deployed static asset directory. Verify existing manual rules and your public asset paths, especially with a custom `base` or output layout.
5. In your own preview environment, check a static asset, an SSR page and an endpoint. Confirm that application-set cache headers and CSP remain unchanged. For a fully static site, only the static checks apply. Use the [worked examples](../guides/static-and-ssr.md) as a reference.

For a v1-style configuration using the compatibility source:

```js
// Before: inside defineConfig(...)
server: {
  headers: { 'X-Content-Type-Options': 'nosniff' },
},
integrations: [astroCloudflarePagesHeaders({ workers: true })],
```

The explicit v2 equivalent is:

```js
// After: inside defineConfig(...)
integrations: [
  astroCloudflarePagesHeaders({
    headers: { 'X-Content-Type-Options': 'nosniff' },
  }),
],
```

Remove `server.headers` only if nothing else in your project needs it. Remove `workers: true`; universal routes now normalize automatically. When you supply `headers`, include every rule you want from the old source: the two sources are not merged. An explicit `headers: {}` opts out of inherited rules.

If upgrading a Cloudflare SSR project from Astro 5 to Astro 6/7 at the same time, treat the move from Pages SSR to Workers as a separate platform migration. This integration does not convert deployment configuration or routes for you.

## Astro and Cloudflare support

The package peer range covers stable Astro 4–7. Install a Cloudflare adapter release whose peer dependencies include the Astro version in your project. Astro 4/5 projects may use Pages or Workers when supported by their adapter. Astro 6/7 Cloudflare SSR projects must use Workers; the official adapter no longer supports Pages SSR. Static output can still be hosted by Pages.

## Use compiled package exports

Import the integration from the package root:

```js
import astroCloudflarePagesHeaders from 'astro-cloudflare-pages-headers';
```

The package now publishes compiled ESM and declarations. Remove aliases or examples that import `index.ts` or `src/` from the package. The middleware entrypoint is available as `astro-cloudflare-pages-headers/middleware` for advanced use.

## Header source and wildcard behavior

Prefer the integration-owned `headers` option. It accepts flat string headers or nested route maps. When omitted, the integration reads final `server.headers` as a compatibility path. When provided, `headers` replaces that source completely; `{}` means no configured rules.

Universal `*` routes now normalize to Cloudflare's `/*` for both Pages and Workers. You can remove `workers: true`; the option remains accepted for source compatibility but is deprecated. If both `*` and `/*` are configured, their values are combined case-insensitively and explicit `/*` values win.

Header routes, names, and values are validated. Mixed flat/nested maps, invalid HTTP field names, non-string values, CR/LF injection, malformed patterns, unsupported route ports, and non-HTTPS host-qualified rules fail with an actionable error.

## Workers response middleware

The official Cloudflare adapter activates middleware automatically. The middleware adds configured values only when the application's response does not already contain that header. Application CSP, nonce-bearing policies, private cache directives, and other app-specific response values keep precedence. Configured static rules are still generated when `runtime: false` disables the middleware. Set `runtime: true` to request middleware with another adapter.

Runtime rules cover responses that pass through Astro, including endpoints and Astro-handled redirects/not-found responses. Direct asset delivery and Worker paths that bypass Astro use static `_headers` or application code. The integration does not create an OPTIONS route or handle exceptions that Astro has not converted into a response.

## Output files and build failures

The integration resolves the adapter's generated static asset path, preserves unowned `_headers` content, and replaces only its marked generated values on subsequent builds. If a custom adapter has an ambiguous output layout, set `assetsDirectory`; a known adapter-generated directory must agree with that override. Source Wrangler files are not modified.

Invalid configuration, an unresolved supported-adapter layout, failed required file operations, or Cloudflare header limits fail the build. `csp.overflow: 'warn'` remains an explicit warning-only escape hatch and does not guarantee that Cloudflare will accept the output.

## CSP migration

CSP auto-hashing stays disabled unless `csp.autoHashes` is enabled. It only scans generated HTML at build time; it cannot hash runtime HTML or make dynamic inline scripts safe. Route mode retains the general CSP fallback and writes per-page replacement rules. Global mode applies the union of generated hashes to each configured policy. A category without an existing directive or applicable fallback remains unrestricted instead of gaining an invented `'self'` policy.

Astro native CSP and integration response-header CSP are independent policies and both are enforced. If both are configured, the integration warns. Choose one owner for script/style rules; it does not rewrite native CSP meta elements or runtime-generated nonces.

Review the final deployed `_headers` and response behavior after upgrading, especially if you previously depended on wildcard `*` remaining literal, duplicate route blocks, app CSP being overridden, or source-only imports.
